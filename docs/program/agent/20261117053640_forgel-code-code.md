## Overview

Наполнить второй публичный репозиторий `code` (организация `forgel-dev`) тонким Python-клиентом `forgel-code`. Клиент не импортирует движок и работает только через уже описанные параметрические команды движка с машинно-читаемым ответом: он не зовёт модель, не читает файлы проекта и не запускает проверки сам. В этом шаге движок не меняется — `forgel chat`, консоль и Telegram продолжают работать как раньше; вынос консоли и последующее удаление заменённого режима чата остаются следующими шагами.

## Goals

- Клиент живёт в репозитории `code` (публичный, организация `forgel-dev`), ставится одной командой и даёт исполняемую команду `forgel-code`.
- Клиент ничего не импортирует из движка: единственный канал связи — запуск `forgel <команда> --json` как отдельного процесса и разбор ровно одного JSON-объекта из stdout.
- Объём по Парето: свободная фраза превращается в задачу; состояние по задаче и по вехе; принять задачу; отправить на доработку с замечаниями; запустить и приостановить работу; разложить цель вехи на задачи; короткая история сессии.

- Ошибка движка (ненулевой код возврата и тело с описанием) доносится до пользователя текстом движка, а клиент завершается с ненулевым кодом и не глотает её.

- Репозиторий содержит README с установкой и списком команд, лицензию Apache-2.0 и собственные тесты.
- Движок в этом шаге не меняется: `forgel chat`, консоль и Telegram остаются работоспособными, файлы движка не правятся.

## Summary

Исправлены два блокирующих замечания ревью в клиенте `forgel-code` (репозиторий `code`), остальная работа предыдущей попытки сохранена.

Что изменено:
- `rework` теперь передаёт замечания движку через `--notes` (`forgel task reject --task <task> --notes "<замечания>" --json`), а не через несуществующий `--reason`. Это реальный флаг `task`-парсера движка, поэтому замечания доходят до движка (FR-3/FR-4).
- `accept`/`rework` больше не отправляют клиентский ключ сессии по умолчанию `local` в `--project`. Ключ уходит в `--project` только после того, как `forgel-code use <key>` успешно принят движком (`forgel use <key>`), и этот факт сохранён в файле сессии (`selected: true`). Без явного выбора проект не передаётся, и движок использует свой активный проект; `local` остаётся локальной меткой клиента и в движок не попадает.
- `use` сохраняет проект в сессию только при успешном ответе движка; при ошибке сессия не меняется.
- README обновлён: таблица соответствия команд движка, `--notes` вместо `--reason`, пояснение, что ключ `local` никогда не отправляется движку как проект.
- Ложный тест-заглушка усилен: подставной движок теперь проверяет контракт аргументов `task accept`/`task reject`/`use` (множество допустимых флагов, включая `--notes`, `--project`, `--task`, `--actor`, `--title`, `--require`, `--accept`, `--constraint`, `--repo`, `--test-command`), поэтому изобретённый флаг вроде `--reason` валит тест так же, как валит движок. Добавлены тесты: ключ по умолчанию `local` не попадает в argv движка; явно выбранный проект попадает в `--project` для `accept` и `rework`; отклонённый движком `use` не меняет сессию; статическая проверка, что сам стенд отклоняет `--reason`.

Проверка: `python -m unittest discover -s tests` — 27 тестов, OK. Файлы движка не изменялись; клиент по-прежнему не импортирует движок и общается только через подпроцесс `forgel <command> --json`.
