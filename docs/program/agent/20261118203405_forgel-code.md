## Overview

The standalone `forgel-code` client (repository `code`) ships with a set of concrete defects: the selected project key is only appended to `accept`/`rework` engine argv while `status`, `tasks`, `task`, `say`, `plan`, `resume`, `pause`, `history`, `projects`, `session` silently fall back to whatever project the engine has active; `--json` and `--engine` are stripped from argv by a hand-written scanner that also mangled phrases containing those tokens and could swallow the value of another option; argparse parse errors escape as plain usage text and a non-zero `SystemExit`, so `--json` callers get no JSON object; the engine call has no timeout, decodes with the process locale, and inherits stdin; a structured engine error (`"ok": false`) with exit code 0 is treated as success and its fields are thrown away; JSON extraction fails when a log line containing `{` precedes the real object, and the failure message can be an unhelpful whole blob or none; task lookup walks the whole payload depth-first and picks an arbitrary nested node with a matching id; missing engine commands are detected by matching English substrings in human text; the JSON envelope reports `project: "local"` even though no project key was ever sent; `--json`/`--engine` and the version string are duplicated across the parser, package and build backend; `plan <milestone> [goal...]` cannot distinguish a goal from a milestone; the sdist is named `forgel-code-<version>.tar.gz` with no `PKG-INFO` (not PEP 625), the wheel only packs top-level `*.py` and drops subpackages and package data, and the README tells users to install from the default branch and from a `.` checkout.

**Outcome:** The client behaves as a thin, honest UI over the engine: the project key selected with `use` reaches every project-scoped engine command and nothing is sent when no project is selected; `--json` always yields exactly one JSON object on stdout, including for argument-parse errors; `--json`/`--engine`/phrase text survive argument parsing unchanged; the engine call is bounded by a configurable timeout, decoded as UTF-8 and detached from stdin; structured engine errors are preserved and never reported as success; the engine's JSON answer is located inside noisy output and diagnosed with an excerpt when absent; task lookup is deterministic and errors on ambiguity; missing engine commands are inferred from return codes and structured fields rather than human text; the version has one source that the build and `--version` both use; the sdist is PEP 625-shaped, the wheel carries every package module and data file; and the README documents a pinned install and an update path. Every one of these behaviours is covered by a test in `tests/`.

## Functional Requirements

- **FR-1**: R1 The project key selected with `forgel-code use <key>` is appended to the engine argv (`--project <key>`) for status, tasks, task, say, plan, resume, pause, history, projects, session, accept and rework; when no project has been selected, no `--project` argument is passed for any of them.
- **FR-2**: R2 With `--json`, any argument-parse error (unknown command, missing or extra positional, unknown or malformed flag) prints exactly one JSON object to stdout with `"ok": false` and a non-empty textual error field, exits non-zero, and stdout contains no argparse usage/help text.
- **FR-3**: R3 `--json` and `--engine` are declared in the argparse parser (once each) and parsed like any other option; no pre-parse scanning of argv removes tokens, so the value of another option is never consumed as an engine path and a reply whose text begins with `-` reaches the engine intact.
- **FR-4**: R4 The engine call is bounded: there is a default timeout, a `--timeout SECONDS` option and a `FORGEL_CODE_TIMEOUT` environment override (precedence: option, then environment, then default). On expiry the client exits non-zero with a message naming the timeout, and with `--json` emits exactly one JSON object with `"ok": false`.
- **FR-5**: R5 The engine's stdout is decoded as UTF-8 regardless of the process locale, and the child process does not receive the client's stdin.
- **FR-6**: R6 When the engine's JSON answer has `"ok": false`, the client treats the call as a failure even if the engine exit code is 0, and reports the engine's structured error fields (code/kind/message as provided) in its own error message and, with `--json`, in the JSON object, instead of substituting raw stdout/stderr text.
- **FR-7**: R7 JSON extraction does not depend on the first `{` being the start of the object: the client locates a decodable JSON object in the engine output; when none can be decoded it raises an error whose message includes a bounded excerpt of the received output.
- **FR-8**: R8 Task lookup by id is deterministic: the client either calls a dedicated engine single-task command or matches only the top-level entries of the engine's task listing on their id/task_id field; if no entry or more than one entry matches, the client reports an error rather than returning an arbitrary node.
- **FR-9**: R9 The absence of an engine command/action is determined from the engine's return code and structured error fields; the client contains no match on human-readable substrings, and the behaviour is the same under any locale.
- **FR-10**: R10 The `project` field of the client's JSON answer is the project key actually passed to the engine, or `null` when nothing was passed; a local session label is never reported as a project.
- **FR-11**: R11 `--json` and `--engine` each appear in exactly one place in the parser and there is no unreachable duplicate declaration; the client version has a single source (`forgel_code/__init__.py:__version__`) that `pyproject.toml`, the build backend and a new `forgel-code --version` all use/print.
- **FR-12**: R12 `forgel-code plan "<text>"` sends `<text>` as the milestone goal; the milestone name is supplied by a separate explicit `--milestone <key>` option. The previous ambiguous `plan <milestone> [goal...]` positional shape is removed.
- **FR-13**: R13 The sdist is `forgel_code-<version>.tar.gz` (PEP 625 normalized name) and contains `forgel_code-<version>/PKG-INFO` at its root; the wheel packages every module of `forgel_code` (including subpackages) and the package data files, not only top-level `*.py`.
- **FR-14**: R14 The README documents installation from a pinned tag, commit or version, documents how to update to a newer pinned version, and states explicitly that editable installs are not supported; it contains no install command pointing at the default branch and no `pip install .` as the recommended path.
- **FR-15**: R15 Every fix above is covered by a test in `tests/` using the existing stdlib `unittest` suite and the fake engine, asserting the engine argv received, UTF-8 decoding under a non-UTF-8 locale, the timeout, and the JSON output shape; behaviour not touched by these defects (command list, successful-answer parsing, human rendering) keeps its current tests and behaviour.
- **FR-16**: R16 Added tests fail against the pre-fix code: each new behavioural test exercises a path that the original implementation gets wrong.

## User Stories

- As a client user I want `use <key>` to make every project-scoped command operate on that project, so that I do not have to re-specify it and cannot accidentally act on another project.
- As a script consuming `forgel-code --json` I want exactly one JSON object on every outcome, including argument errors, so that I can parse stdout unconditionally.
- As a user typing a phrase that contains `--json` I want the phrase delivered verbatim, so that my reply is not silently altered.
- As a user of a slow or hung engine I want a bounded wait with a clear message, so that the client never hangs forever.
- As a user on a non-UTF-8 machine I want engine output decoded correctly, so that non-ASCII text is not mangled.
- As a user reading an error I want the engine's own structured reason rather than a raw dump, so that I can act on it.
- As an operator I want to install a pinned version and know how to update, so that deployments are reproducible.

## Risks

- The engine's exact semantics for `plan` are not fully read here: if the engine requires a milestone positional, `forgel-code plan "<text>"` will surface a structured engine error rather than plan anything, leaving R12 only partly useful.
- If the engine has no single-task read command, R8 forces top-level matching of the task listing; an engine that nests task records in another top-level container would then report 'not found'.
- Choosing the first decodable JSON object can pick a stray structured log line that happens to be a JSON object; the intent only requires that a `{` inside free text does not break parsing.
- The engine error payload shape may vary between versions (string vs object); carrying 'its fields' through has to degrade gracefully.
- Timeout tests that rely on real sleeping are slow and can be flaky on loaded CI machines.
- Locale-specific tests depend on the available locales in the test environment; setting `LC_ALL`/`LANG`/`PYTHONIOENCODING` may not be enough on every platform.
- The task intent cites decision D-025 for English public texts, but the supplied decision log only lists D-001..D-007; the English-text constraint is therefore carried from the task intent, not from a recorded decision.
- Touching the version source can desynchronise `pyproject.toml`, `_build_backend.py` and `__version__` if only one is updated.

Ответ `{"ok": false}` с кодом выхода 0 теперь ошибка, а структурные поля ошибки (`code`/`kind`/`message`) переносятся в `EngineError.payload` и в текст сообщения вместо сырого вывода. Извлечение JSON больше не опирается на первую `{`: перебираются все позиции `{`, берётся первый декодируемый объект, при неудаче в сообщение попадает ограниченная однострочная выдержка.
