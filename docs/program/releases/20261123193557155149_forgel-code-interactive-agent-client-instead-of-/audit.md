Three non-blocking issues remain: the English/Russian sensitive-action matcher over-blocks ordinary `verb + project` sentences, the sensitive refusal points only at `forgel-code` (which reopens the session) rather than the explicit subcommand, and the README's interactive section contradicts itself on when a clarification is returned.

## Findings

- [minor] code: `_asks_for_explicit_action` pairs broad create verbs (`make`, `generate`, `init`, `provision`, …) with the noun `project`/`projects`, so ordinary requests that are not project creation — e.g. `make the project faster` or `generate the project documentation` — are classified as sensitive, refused, and never forwarded to the engine, although the guard task requires requests outside the guarded categories to be forwarded as before. The ordinary-conversation tests only exercise sentences that name the object without a verb, so this class is untested. — Restrict the project-noun rule to genuine creation frames (the create verb taking the project as its direct object) and add regression tests for ordinary `verb + … + project` sentences that must still reach the engine.
- [minor] code: The sensitive-request refusal names only the program `forgel-code`, not the explicit operation. Running `forgel-code` without arguments reopens the same interactive session, so the advertised next step cannot perform the requested action and the owner must guess the real subcommand, which is what the requirement asked the refusal to name so the owner can act without guessing. — In every language's sensitive refusal, name the concrete explicit command(s) for the requested family (adopt, project create, secret/config operations) instead of only `forgel-code`.
- [minor] code: The README's interactive section contradicts itself: it says "Each sentence is handed to the engine's project agent" and its table maps "a plain sentence" to the agent's answer, but the next paragraph says "A sentence that names no action, or more than one, gets a clarification and nothing is carried out." A plain sentence names no action, so the documentation gives two different behaviours for the same input and conflicts with the requirement that a typed phrase is answered by the agent. — Reword the paragraph to state the actual rule — a clarification is returned when a sentence targets an action on a task but names no task, no available action, or several actions — so it no longer contradicts the table and the agent-answer behaviour.
