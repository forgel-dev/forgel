# Release audit 20261124145530795459_make-forgel-and-forgel-code-install-and-run-as-o

- Round: 1
- Verdict: fail

## Summary

The release cannot be published as a working pair. The Forgel Code installer assumes an engine-installer command and version-report shape that the engine repository does not provide: it calls `forgel-install --source ... --available-version/--install`, while the engine ships `install.sh` with `--resolve`/`--uninstall` and environment-based inputs. It also reads an installed engine through `forgel --version --json` with a nested `engine.version`, while the documented engine report is `forgel version --json` with a top-level `version`. The combined-install tests use a stub that mirrors the incorrect contract, so the release's central acceptance criterion is not verified. Additionally, the main repository diff contains unreviewed product-code changes outside any listed task.

## Findings

- [critical] code: The combined installer invokes `"$ENGINE_INSTALLER" --source ... --available-version` and `--install VERSION`, defaulting to `forgel-install` on PATH. The engine repository ships `install.sh` with `--resolve` and `--uninstall` and takes source/ref through `FORGEL_SOURCE`/`FORGEL_REF`; it does not provide a `forgel-install` command or those flags. A clean default Forgel Code install therefore fails in the engine phase and cannot produce the promised working pair. — Define one cross-repository installer contract and implement both sides: either add an installed `forgel-install` command with `--source`, `--available-version`, and `--install VERSION` to the engine, or make Forgel Code invoke the engine's actual `install.sh`/documented command with `FORGEL_SOURCE`/`FORGEL_REF` and `--resolve`. Update both READMEs and add a cross-repository end-to-end test.
- [major] code: `engine_present_version` runs `forgel --version --json` and reads `payload["engine"]["version"]`. The engine's documented report is `forgel version --json`, whose single JSON object carries the version at top-level `version`. A real installed engine is therefore treated as absent or unreadable; the installer can install an offered version that is equal to or older than the present engine, defeating idempotency and possibly downgrading an existing engine. — Invoke the documented `version --json` command and parse the top-level `version` (or accept both documented shapes). Add a test using the engine's real reported JSON shape so an installed engine is correctly kept.
- [major] code: The combined-install tests use `tests/stub_engine_install.py`, which encodes the same assumed `forgel-install` interface and nested engine JSON. No test runs the actual engine installer or the actual engine version report, so the release's required one-command pair and idempotent keep/replace behavior are not verified against the other repository. — Add an integration test that executes the real engine `install.sh`/`forgel version --json` contract, or generate and validate the stub against that contract. Update the tests so they fail on the current contract mismatch.
- [major] main: The main repository diff contains changes to `src/forgel/daemon.py` and `tests/test_daemon.py` that are not listed in any task's `files_changed` and are not covered by the task reviews, which claim only the installer/documentation files. Shipping unreviewed product-code changes in this release is unaccounted for and risks regressions outside the install/version work. — Remove these changes from the release, or attach them to a task, specification, and review that justify and verify them.
