**Version:** 0.4

**Status:** key decisions locked
**Product:** Forgel. Domain: `forgel.io`.

## 1. What We Are Building

Forgel is an open-source autonomous software studio for building and operating cloud services.

The user talks to it through a chat interface (Telegram) and describes a product. Forgel:

1. Turns the brief into structured requirements.
2. Selects a **recipe** — a validated composition of plugins (stack + infrastructure + integrations) from a known registry.
3. Splits the work across repositories and features.
4. Runs development, review, independent QA and acceptance.
5. Deploys to staging; after launch it watches metrics and prepares changes.

**Two delivery forms:**

- **OSS** — the user installs it on their own server, brings their own API key and their own cloud. The first and primary release.
- **Hosted** — the same thing out of the box, with no installation. Later, after the OSS release.

**Humans remain only where an action is legally or platform-wise impossible to automate:** incorporating a legal entity, opening a payment account, publishing to app stores, approving a production deploy, and acknowledging compliance responsibility.

Jurisdiction is part of the product, not a document attached at the end. Forgel applies a jurisdiction pack to every project. A draft pack is usable; production approval includes an explicit acknowledgement that the user is responsible for regulatory compliance. Forgel is not a law firm and does not certify compliance.

Forgel is a tool, not a closed pipeline. It can run the whole lifecycle, or coexist with other tools: a prototype generated by Forgel can be finished by hand or in another harness. The process must not break when code changes outside it. Git is the source of truth; external edits are detected and reconciled, never overwritten.

Forgel runs as a long-lived control-plane process. It never polishes endlessly: each iteration has a finite goal, a definition of done and a budget. When the goal is met or the budget is exhausted, the iteration closes with a recorded verdict, and the daemon waits for the next trigger.

The immediate goal is self-hosting: Forgel develops itself through its own daemon and Telegram interface. Another harness may be used for bottlenecks, but it is not the main development environment.

### Who It Is For

- **Developers and teams** who need control over their code, cloud and model.
- **Product teams and studios** that need delivery capacity without giving up control.
- **Not for** those who want no-code without access to the code and infrastructure.

### Brand and Positioning

**Name:** Forgel (a coinage from *forge*; domain `forgel.io`, GitHub org `forgel-dev`, packages `forgel`).

**Category:** open-source autonomous software studio.

**One-liner:** Forgel is an open-source software studio that turns a brief into a working product on your own infrastructure.

**Tagline:** "Brief in. Product out. Your cloud."

**Brand pillars:**
1. **Own it** — your server, your model key, your code.
2. **Prove it** — spec → review → independent QA → acceptance; jurisdiction evidence and an auditable trail.
3. **Extend it** — plugins for stacks, clouds and QA; a recipe registry.
4. **Coexist** — use Forgel end-to-end or alongside other tools; external edits are first-class and never overwritten.

**What we are not:** not a code generator, not no-code, not an agency. We hand over repositories and a running staging environment.

## 2. MVP Scope

### In Scope

- A web product: backend + frontend.
- One backend stack: Django (DRF) — preset #1.
- React SPA.
- Postgres + S3-compatible object storage.
- One cloud provider: Yandex Cloud.
- Telegram as Forgel's own interface.
- One jurisdiction pack: a draft for M0, a more complete pack for M1 (legal review optional).
- Multi-repo from day one.
- Forgel ships as a Docker image with a Compose quickstart.
- Generated projects ship a `Dockerfile` and a `compose.yaml`, plus `FORGEL.md`, `AGENTS.md` and `forgel.toml`.
- Independent end-to-end QA in an isolated Compose stand with a headless browser.
- Staging deploy with human approval.
- Cost tracking and acceptance metrics from day one.

### Out of Scope

- Mobile apps.
- A second cloud.
- Fully automatic production deploys.
- Regulated domains: dating, gambling, health, children.
- Hosted hosting and billing.
- Telegram integration inside the generated product (that is a separate plugin, not Forgel's chat interface).

| **D-012** | Human gates at irreversible points | Production, legal entity, payments, app stores | The core can stop and request an action with instructions |

| **D-015** | Refusal is a feature | Regulated domains need a human and a lawyer | The system explicitly says "I won't take this" and explains why |

| **D-022** | Model routing is a core policy, not an agent's choice | Cost and quality must be controlled centrally; review must stay independent | A role → model map in config, with cost attribution; an agent cannot upgrade its own model |
| **D-023** | Process prohibitions live in code, not only in documentation | A written rule gets bypassed: the precedent was a repeated full QA run | Gates, the ledger and runners refuse the violation; prose is an explanation, not a mechanism |
| **D-024** | A change set is the unit of planning and acceptance; dependencies between repos are explicit edges | A single repository cannot see integration; the product ships as a set of versions | `program.yaml` holds the graph; a blocked status always names the edge and the path to unblock |
| **D-025** | Repository documents are in English; chat and internal docs are in Russian | The product is international; public documents are part of the product surface | Every committed document, README and public issue is in English; `INTERNAL.md` stays Russian and gitignored |
| **D-026** | Jurisdiction is a first-class layer supplied by a `jurisdiction` plugin and consulted by the core | Law dictates how a product must be built in some markets: data residency, consent, payments, advertising, moderation, incident reporting. These are product constraints, not deployment details | Intake captures jurisdiction; recipe selection filters by it; spec, QA, acceptance, audit and deploy gates consult it; a draft pack is usable and production requires the compliance acknowledgement |
| **D-027** | Legal rules are versioned data with citations, effective dates and a review date; the LLM maps and explains but never certifies | A prompt cannot be an authoritative legal source, and stale law is worse than no law | Each pack has `status`, `reviewed_by`, `review_due`; deterministic checks where possible; ambiguous cases go to human review |
| **D-028** | Jurisdiction packs are advisory; production approval includes an explicit compliance responsibility acknowledgement | A draft pack is better than an ignored jurisdiction, and small teams cannot fund legal review for every project | The system records the pack, its status and the disclaimer; it does not block on a missing or draft pack; the human who approves production carries responsibility |
| **D-029** | Context files: `FORGEL.md` is native, `AGENTS.md` is the cross-harness canon, `CLAUDE.md` is a local compatibility shim | One source of truth avoids drift; a public `CLAUDE.md` advertises another harness and contradicts dogfooding | Forgel reads `FORGEL.md` → `AGENTS.md` → `CLAUDE.md`; generated projects get `FORGEL.md` + `AGENTS.md`, never `CLAUDE.md` |
| **D-030** | Docker is the default execution substrate: the core defines a sandbox contract, Docker/Compose is the reference implementation, providers and QA drivers are plugins | Reproducible environments, dev/QA/prod parity, one-command self-host, and isolated E2E runs | Forgel ships as a Docker image; generated projects get `Dockerfile` + `compose.yaml`; QA runs in an isolated Compose stand; the sandbox interface allows other runtimes later |
| **D-031** | The browser engine is a QA driver plugin: Playwright/Chromium is the default; Lightpanda is an experimental CDP driver for non-visual checks | Visual QA needs rendering and screenshots; Lightpanda is much lighter but has no graphical rendering, ships nightly, and is AGPL | Scenarios are driver-agnostic; Chromium is used for visual checks; Lightpanda is evaluated on real scenarios before adoption |
| **D-032** | Forgel is composable and non-exclusive: external edits are first-class | Users may prototype with Forgel and finish by hand or in another harness; lock-in kills adoption, and the process must survive code changed outside it | Git is the source of truth; a reconcile step detects external changes; Forgel never resets or overwrites them |
| **D-033** | Reconcile, don't regenerate | External changes may be intentional; regenerating would destroy them and break the user's work | Read the current files, diff against the last known state, update the spec and acceptance, and continue in a new ledger generation that re-runs the affected gates |
| **D-034** | Project config is `forgel.toml` (TOML, standard library) with `project`, `qa`, `jurisdiction`, `models` and `budget` sections | TOML is explicit, readable, and parsed without dependencies; config is a project artifact, not hidden state | The generated project carries `forgel.toml`; explicit runtime settings win over it, which wins over defaults |
| **D-035** | Forgel runs as a long-lived control plane with finite iterations: each has a goal, a definition of done and a budget | An always-on orchestrator must stop when the goal is met; endless polishing burns budget without improving the product | The daemon runs pending work, then idles; an iteration closes with a recorded verdict when acceptance/audit pass or the budget is exhausted |
| **D-036** | Post-release work is triaged into auto-fix, ask-user and record-only | Money-path, security and regression defects must be fixed immediately; ambiguous or risky changes need the user; low-signal issues need more data | Auto-fix critical, reversible, high-confidence findings; ask on ambiguity, scope, migrations and legal; record low-signal issues and revisit on a threshold |
| **D-037** | Every iteration has a budget cap and stops on exhaustion | Unbounded retries and improvement cycles are the main cost risk | Budget from `forgel.toml`; exhaustion stops the iteration, records the verdict and leaves deferred work explicit |
| **D-038** | After the user's goal is met, Forgel proposes only PATCH fixes by default; MINOR is opt-in and MAJOR is human-initiated | The product is done when it meets its requirements; endless polishing burns budget and loses control | SemVer classifies every post-release proposal; the default is a proposal with evidence, not an automatic change |
| **D-039** | Automatic PATCH application is opt-in and off by default | Automatic changes after the goal carry regression and infinite-loop risk | `release.auto_patch = true` enables it; proposals without approval are recorded, not applied |
| **D-040** | Simplicity is a gate: every patch has a complexity budget for added lines, new config keys and compatibility markers | Models accumulate requirements, branches and shims; complexity compounds and becomes unmaintainable | Review fails over budget until the patch is simplified, the spec is changed, or the budget is consciously adjusted |
| **D-041** | A clean-context Simplicity Arbiter reviews necessity, not just correctness | The developer's context normalises its own complexity; an independent role can ask whether a branch, flag or shim should exist at all | The arbiter reads the spec, diff and complexity report, and returns simplify / accept / escalate |
| **D-042** | The arbiter auto-applies safe internal simplifications, asks only on user-visible, irreversible or ambiguous changes, and records every decision | Asking on every change breaks automation; deciding everything silently loses control | Dead-code, unused-flag and unclaimed-shim removals are automatic; user-visible behavior, public contracts, money, legal and data-model changes are escalated; the rest is decided and recorded in an ADR |
| **D-043** | Refactoring is exception-based, not the default; it requires a proposal comparing extension and maintenance cost against refactor cost | Agents often append branches where a small rewrite is cleaner, but refactoring for every requirement creates its own loop | Default is NO_REFACTOR; a proposal names the current design, the new requirement, both costs, risks and alternatives |
| **D-044** | Refactoring decisions are NO_REFACTOR, TARGETED_REFACTOR, STRUCTURAL_REFACTOR and DEFER | One rule cannot cover a local cleanup and a cross-module rewrite | Targeted, internal, behavior-preserving refactors that reduce net complexity may be auto-applied; structural refactors need a proposal and human approval; debt is recorded with a trigger |
| **D-045** | Append-only growth is a signal for the arbiter, not an automatic failure | Extending existing code is usually correct; a rewrite needs cost/benefit judgment | The complexity report surfaces append-only files; the arbiter decides NO_REFACTOR / TARGETED / STRUCTURAL / DEFER |
| **D-046** | Budget control is a core requirement with hard caps at feature, iteration, day, project and provider-key level | An agent stuck on a misconfigured environment can consume the provider balance, and with auto top-up the card balance; DeepSeek does not enforce a per-key limit | The harness reserves, records and enforces cost before every model call; hard stop at the cap, never a silent overrun |
| **D-047** | A Budget Arbiter may pause or stop, but never increase a budget | Only the user can accept more spend; an agent must not raise its own ceiling | Every stop records the reason and the checkpoint; the user raises the budget, then the iteration resumes |
| **D-048** | Provider keys are scoped, prepaid and isolated; auto top-up is disabled; a single egress proxy is the only path to the model | The provider cannot enforce the budget, and subagents must not bypass the ledger | One key per project/environment, no main key, proxy cap; the ledger is the source of truth for spend |
| **D-049** | GitHub integration uses a GitHub App with short-lived installation tokens; no personal token by default; no direct push to `main` | Short-lived, repo-scoped tokens limit the blast radius; protected `main` keeps a reviewable history | The daemon mints a token per job, clones/fetches, pushes a branch and opens a PR; tokens never touch disk or logs |
| **D-050** | One branch and one PR per change set; bot identity; protected `main`; **auto-merge is the default**, human merge is an opt-in mode | Mandatory human merge turns Forgel into a copilot-like assistant and breaks the end-to-end automation promise | Auto-merge after all gates and required checks pass; `merge = "human"` for teams that want a final review |
| **D-051** | Fetch before every iteration; rebase on upstream movement; a conflict stops the iteration | Other people and tools push too; force-push would destroy their work | Never `reset --hard` or force-push; conflicts are surfaced to the user |
| **D-052** | Repo onboarding is a PR; the daemon runs from a released image, not the working copy it modifies | Adopting a repo must be reviewable; a running process must not rewrite its own code | `forgel adopt <repo-url>` opens an onboarding PR; Forgel changes ship via CI-built images |
| **D-053** | Auto-merge requires all gates, green CI, no blocking reconciliation, budget within cap, no conflict and a PATCH/MINOR change set; post-merge verification auto-reverts on failure | Removing the human merge must not remove the safety net | A merge queue serializes merges; failed post-merge smoke triggers an automatic revert and a stop; MAJOR changes remain human-initiated |
| **D-054** | Production deploy has three modes: `auto` (opt-in, not recommended), `confirm` (default when configured) and `manual` (no pipeline) | Full automation must be possible, but a human confirmation is a cheap last gate for an irreversible action | `confirm` asks in Telegram and records the approval; `manual` produces a release bundle and instructions; `auto` requires explicit config and a compliance acknowledgement |
| **D-055** | The chat gateway is a dependency-free Telegram long-poll adapter, closed by default, hosted in the same process as the daemon | Self-hosting should need one process and no extra services; a bot that can spend money must not be open to strangers | `forgel telegram` polls with `urllib`, requires `TELEGRAM_ALLOWED_CHAT_IDS`, maps commands to core functions, and runs pending iterations between polls |
| **D-056** | Staging approval is a pipeline stage scoped to one generation; production approval requires a completed, approved release and the compliance acknowledgement | An approval given for one release must not carry over to a new generation, and a production decision must be explicit | The pipeline parks at `approval`; approvals live in the ledger and `docs/program/approvals.md` with the reviewed release SHA; production approval without the acknowledgement is rejected |
| **D-057** | The chat has a selected project per chat session; a message without a command goes to that project's agent | One daemon serves many projects, and the user should not repeat an id on every line | The ledger stores `chat_id → project_id`; `/new` selects the new project, `/use` switches, `/projects` shows the selection |
| **D-058** | Project contexts are isolated by construction: no shared agent instance, prompt cache or conversation between projects | A leak between customer projects is the most serious failure a studio can have | Every agent call builds context from one project root and its history file; a test asserts that another project's brief and files never appear in the prompt |
| **D-059** | Configuration is split into daemon and project layers; secrets are separate and never stored in project artifacts | Polling cadence and the model endpoint belong to the installation, while QA, budget and release policy belong to the project | Daemon keys live in `$FORGEL_HOME/config.toml`; project keys in `forgel.toml`; `/config` shows the value and its source; secrets live in env or a `0600` file |
| **D-060** | Secrets may be set from the chat only through a one-time command that deletes the message; env and the local CLI take precedence | Telegram bots have no end-to-end encryption, but typing a key on a server during MVP development is too slow | `/secret set` deletes the message, stores a `0600` file, never echoes the value and warns about the channel; `forgel secret set` over SSH is the production path |
| **D-061** | A project is a container: a `program/` control repository for specs and configuration plus real git repositories under `repos/<id>/` | One project can span a backend and a frontend; a flat workspace hides repository boundaries and makes independent history impossible | New projects use the container layout; legacy flat projects remain readable; sync, QA and the template migrate to the container |
| **D-062** | Repository hosting is a provider plugin; GitHub is the first implementation | Other teams use GitLab, Gitea or a private server, and the core must not depend on one host | A provider contract covers auth, clone, branch, push, pull request and merge; the in-tree GitHub provider is the reference implementation |
| **D-063** | A project can be created by adopting an existing repository, and repositories can be added later; control files live outside the code repositories | Users already have code, and a project often grows a repository after it starts | Adoption clones into `repos/<id>/`, initializes `program/` (`forgel.toml`, `program.yaml`, context files) and never regenerates code; `repo add` extends the container |
| **D-064** | Repositories are grouped in a project by dependency edges, not by theme | The value of a multi-repo project is that a change in one repository has a contract consequence in another; unrelated repositories gain nothing from grouping | `program.yaml` records `depends_on`; `/repo add` and `/repo link` set edges; independent repositories are allowed and maintained separately, and the UI says the grouping adds no coupling |
| **D-065** | GitHub auth resolves a GitHub App installation token first, then a PAT; the App path is an optional crypto extra, and deploy keys are clone/push-only | App tokens are short-lived and the right production default, but a PAT keeps the M0.5 self-host bootstrap free of extra dependencies; a deploy key cannot open a pull request | `github.auth = auto` tries the App when configured and falls back to a PAT; `cryptography` is imported lazily from the `github` extra; a deploy-key setup refuses pull-request operations |
| **D-066** | The coding agent uses a JSON action protocol with a bounded loop, not provider-specific tool calling | Any chat model can drive it, and the same protocol works over a provider API, a scripted client or a file bridge to a local subagent | One action per turn (list/read/write/delete/run/done/fail), paths confined to the repository, a command allowlist, secret-free child env, a step cap, a final test command and a report |
| **D-067** | The migration e2e is a manual, budget-gated harness with deterministic product checks and separate harness checks | The result depends on the model; a harness failure must be distinguishable from a model-quality failure, and a local subagent run must not spend provider budget | `tests/e2e` builds a minimal blog with `script`, `bridge` or `api` modes; `validate_blog.py` is an external validator; harness checks cover daemon/task/report/commit lifecycle; runs only on explicit instruction |
| **D-068** | A plain chat change request becomes a coding-agent task; the intake agent fills explicit requirements, acceptance, repository, constraints and test command | The chat is the product interface and should not stop at a recorded request; the executable unit is a task the daemon can run and the user can inspect or cancel | The intake agent returns a structured change request; the task is stored in `docs/program/tasks/`, shown by `/tasks`, cancellable with `/task cancel`, and executed by the daemon; ambiguous multi-repository requests are questions, not guesses |
| **D-069** | Deployment is a local SSH utility driven by `.env.deploy`; the image is pushed to a registry or built remotely, the remote env is written with mode `0600`, and the server needs only SSH + Docker + Compose | Manual SSH configuration is the main source of deployment mistakes, and configuration must stay easy to change as the installation evolves; the server should not need a toolchain | `forgel deploy up` checks SSH/Docker/Compose, offers a consent-based install when root or passwordless sudo is available, otherwise prints manual commands; it builds/pushes or remote-builds, uploads the Compose file and filtered env, starts the service and runs the doctor; secrets never appear in argv or logs. SSH user, port and key are optional (config/agent/default key). |
| **D-070** | The daemon container drops to an unprivileged user; project code runs only in the local single-tenant sandbox, and the host Docker socket is never mounted | Project tests are untrusted code; container root plus host Docker access would turn a test into host compromise, while local execution is acceptable for a single trusted operator | `deploy/entrypoint.sh` chowns `/data` then drops to UID/GID 10001; agent commands get a stripped env; `FORGEL_SANDBOX=docker` is implemented by D-073 as a per-project sandbox (separate daemon, one repository mounted, non-root, no capabilities); the host socket is not part of any Compose file |
| **D-071** | A project environment is a declarative container artifact (OCI image or Dockerfile/Compose/Dev Container) plus a small contract for `setup`, `test` and `e2e` commands; the core contains no per-language command adapters | Knowing every toolchain's current commands in the core goes stale and creates permanent maintenance, while per-instance scripts fragment the ecosystem | The environment is a committed project artifact; Forgel reads the contract and runs it in the sandbox; official recipes are only starting points |
| **D-072** | Official recipes cover common stacks as convenience templates; the coding agent may create or extend an environment definition for a missing stack, but only through the standard contract and with review | Maintaining every environment is impossible, and forbidding new ones caps the product; a standard, reviewable artifact avoids bespoke per-instance adapters | Recipes are small composable starting points; the agent writes a Dockerfile/Compose/Dev Container and `environment.yaml`; nothing language-specific enters the core |
| **D-073** | Arbitrary environment code runs only inside a per-project sandbox: repo-only mount, no `/data` secrets, no host Docker socket, resource and network limits, configurable registry policy | Broad environment support is safe only behind an isolation boundary; CI runners solve the same problem the same way | The sandbox runtime builds/pulls and runs the project image; the daemon talks to it; a trusted single-user host may allow arbitrary images, while hosted mode uses an allowlist and pinned digests; `local` remains a single-tenant fallback. One labelled container per session mounts the working repository at `/workspace` and the declared sibling repositories read-only, runs as the daemon UID/GID with capabilities dropped, a read-only root and `/tmp`, CPU/memory/pid limits and `network=none` by default; the daemon reaches it over `DOCKER_HOST`, never the host socket. The bundled DinD sidecar is opt-in and privileged; a remote daemon is the multi-tenant choice |
| **D-074** | The core moves to Apache-2.0; the moat is the brand, execution speed, the audit/benchmark data and the future hosted service, not copyleft | The project bets on adoption and virality: AGPL deters companies from embedding and extending the core, while a hosted clone is now unlikely to beat the original on trust, audit and distribution | All code is Apache-2.0 (DCO, no CLA); registry data stays CC0 and docs CC BY 4.0; the trademark and the `conformant` badge remain; a closed hosted clone is answered by brand, data and service quality. Supersedes the core-license part of D-018 |
| **D-075** | Human involvement is an exception, not a step: agents work autonomously through pre-release work, show a finished result with evidence, and rework on feedback; they stop only for a material fork, an irreversible or destructive action, or missing access | Constant confirmation is the main bottleneck of agent-driven development, while the earlier safety over-correction now costs more than it protects; pre-release work is reversible, so doing and showing beats asking | Prompts and `AGENTS.md` state the policy; every assumption is recorded in the task and report; production, product data, payments, secrets and legal decisions stay human-gated; one consolidated question, never a dialogue |
| **D-076** | Repository lifecycle is a Forgel command, not manual GitHub work: the project can create a repository in the configured organization and publish the existing local repositories from the CLI or chat | A project grows past ten repositories, and every manual creation step blocks the autonomous loop; the same operation is a deterministic, auditable API call | `repo create` creates the GitHub repository, initializes the local repository, registers it in `program.yaml`, pushes and records a ledger event; `repo publish` creates remotes for existing local repositories; private by default, no deletion and no force-push; the org comes from `[git] org`, `--org` or `FORGEL_GITHUB_ORG` |

Business-model and jurisdiction decisions are not part of this public document. Numbering is continuous: D-014 is an internal business decision.

### Licensing Model

| Component | License | Why |
|---|---|---|
| Core (orchestrator, runtime, ledger) | Apache-2.0 | Maximum adoption and embedding; the moat is brand, speed, data and the hosted service (D-074) |
| Plugin SDK, API schemas | Apache-2.0 | Plugin authors are not forced to open their code |
| Official plugins and templates | Apache-2.0 | Studios can use and modify them without output contamination |
| Recipe registry | CC0-1.0 | Data should be free |
| Documentation | CC BY 4.0 | Maximum distribution |
| Generated code | The user | An explicit Output License: no copyleft on the customer's product |
| Hosted control plane (later) | Apache-2.0 — proposal, Q3 | Consistency with the core; monetization is hosting, support and the managed experience |

**Trademark:** the Forgel name and logo are protected; a fork must rename itself. The `conformant` badge is issued only to plugins that pass the conformance kit.

## 4. Architecture

```
┌──────────────────────────────────────────────────────────────┐
│ CONTROL PLANE                                                │
│  Chat gateway (Telegram / web)                               │
│  Intake → Recipe selector → Orchestrator (state machine)     │

### Core Components

1. **Chat gateway** — Telegram for the MVP, web later.

9. **Gates** — checks that guard transitions between stages.

### Rules

- **Contract-first is mandatory.** The backend publishes OpenAPI 3.1; the frontend and mobile consume generated clients. Without this, cross-repo drift is the main failure mode.
- **Brownfield adoption.** Forgel can adopt existing repositories; it does not require that it created them. The manifest describes the current graph, not a pristine generation history.
- **Change set.** A feature may touch several repos. Acceptance happens at the change-set level, not per repo: otherwise every repo is green while integration is broken.
- **Dependency graph** determines build order and what can run in parallel.
- **Integration environment** is built from pinned SHAs of all repos.
- **Lockfile** stores repo SHAs and plugin versions — reproducibility months later.
- **Agent isolation:** a separate worktree per task, task claiming in the ledger, a merge queue per repo.
- **One reviewer per repo**, but the final audit covers the whole change set.

### First Provider Profile (Yandex Cloud)

- The `yandex` Terraform provider is the basis of the adapter; no hand-written SDK.
- Compute: Serverless Containers (revisions make rollback possible) or a Managed Instance Group — decide by the conformance run.
- Database: Managed PostgreSQL.
- Storage: Object Storage (S3-compatible) — the same interface as international S3.
- Registry: Container Registry.
- Secrets: a service account with minimal roles and a short-lived IAM token.
- Provider details stay inside the plugin; the core knows nothing about Yandex.

  },
  "conformance_report": "sha256:..."

```

### Selection Algorithm

1. Brief → `requirements.json` (LLM, structured output, JSON Schema).
2. Deterministic matcher: filter by `constraints`, discard mismatches.
3. Ranking: maturity, conformance, cost, requirement coverage.
4. The LLM chooses from the **top 3** and records the rationale in an ADR.
5. If ambiguity is high, ask the user in chat (2–3 options in plain language).
6. If no recipe fits, refuse explicitly and explain what is not supported.

In the MVP the LLM **cannot** assemble a recipe from individual plugins. Composition comes only from the registry.

### Conformance Kit

The core runs a fake project against a plugin in a sandbox:
`provision → apply → verify → rollback → destroy`.
A plugin that fails the kit does not enter the registry with `conformant` status.

### Plugin Security

- The process is isolated; access is limited to declared capabilities.
- Secrets are short-lived, scoped tokens per operation, never ambient credentials.
- An egress allow-list comes from the manifest.
- Plugin signing, a lockfile, and no postinstall scripts.
- For the agent, plugin content (templates, docs) is untrusted data, not instructions.
- Third-party plugins require explicit user confirmation.

### Jurisdiction Layer (First-Class)

Jurisdiction is not a document attached at the end. It is a layer every stage consults, supplied by a `jurisdiction` plugin and enforced by the core. The purpose is to make the default path easier — requirements that are always needed should not be retyped for every project — not to block delivery.

**Why it is first-class.** In some jurisdictions the law dictates how a product must be built: where personal data is stored, which consent flow is required, how payments and advertising are handled, what content must be moderated, how incidents are reported. These are product constraints, not deployment details. A generated product that ignores them is not a finished product.

**Pack.** A jurisdiction pack is versioned data:

```yaml
id: ru
version: 2026.11
status: reviewed          # draft | reviewed | expired
region: ru
effective_from: 2026-11-01
reviewed_by: "legal counsel"
review_due: 2027-11-01
legal_sources:
  - id: ...
    title: ...
    url: ...
mandatory_requirements:
  - id: RU-PD-001
    title: ...
    applies_when: ...
    requirement: ...
    verification: deterministic   # deterministic | manual | legal_review
    evidence: ...
prohibitions: []
required_evidence: []
```

Rules are data, not prompts. Deterministic checks are preferred; ambiguous cases go to human legal review. The LLM may explain a rule and map it to a requirement, but it never certifies compliance.

**Where it applies:**

| Stage | What the layer does |
|---|---|
| Intake | Captures jurisdiction, entity type and operating regions. |
| Recipe | Filters out incompatible recipes, providers and model endpoints. |
| Architecture | Adds data-flow, residency and retention constraints. |
| Spec | Injects mandatory requirements and prohibitions as hard constraints. |
| QA | Runs deterministic compliance checks. |
| Acceptance | Requires the evidence matrix and marks production readiness. |
| Audit | Includes the jurisdiction report and the pack version. |
| Deploy | Records the pack and its status; requires the compliance acknowledgement at the production gate. |
| Operations | Tracks ongoing obligations: incident notice deadlines, retention, reporting. |

**Default rule.** No pack → the generic draft is used and the gap is recorded; the project is not refused. Draft or expired → requirements are applied, production is allowed with the compliance acknowledgement. Reviewed → stronger evidence, but still not a legal guarantee. The layer informs; the human production gate decides. The plugin supplies the data; a human carries responsibility.

**Compliance disclaimer.** Forgel is a software development tool, not a law firm. Jurisdiction packs are draft guidance, may be incomplete or out of date, and are not legal advice. Forgel does not warrant that a generated product complies with the laws of any jurisdiction. The user is responsible for regulatory compliance; approving a production deploy confirms that responsibility.

**Production gate.** The production deploy command requires an explicit acknowledgement (for example `--accept-compliance-responsibility`) and records the pack id, status, disclaimer hash and the acknowledgement in the deploy record.

### Role Contract (Clean Context)

| Role | Reads | Does not read | Writes |
|---|---|---|---|
| Spec writer | master plan, repo requirements, brief | code, QA reports | feature doc |
| Spec reviewer | brief, master plan, feature doc | code, agent history | findings |

Jurisdiction review is a human gate. No agent certifies legal compliance; the core only enforces the pack and records the evidence.

### State and Resumability

- Append-only ledger: `project_id`, `generation`, `task_id`, `stage`, `status`, `attempt`, `idempotency_key`, `artifact_refs`, `cost`.
- A checkpoint after every stage; the artifact is committed before the transition.
- A reconcile starts a new generation. Old events stay as history; the affected gates run again for the new generation.
- Resumption starts from the last committed state, not from agent memory.
- A crash must not leave half-applied infrastructure: plugins must implement `rollback` and `destroy`.

### 7.1 Proven Practices

Practices proven in production; Forgel inherits them as role, document and gate templates.

| Practice | How it is used |
|---|---|
| Feature doc: FR/NFR with IDs, non-goals, acceptance criteria, open questions, revision history; no implementation code | Spec template; document version separate from product version |
| Changing an existing feature: a `## Fix`/`## Addition` section in its doc, not a new file | The spec lives, it does not multiply |
| Developer reads the spec, follows existing patterns, lints, writes a QA case, reports files/decisions/verification | Role contract |
| Reviewer builds a requirement → code → evidence traceability matrix and returns PASS/NEEDS_WORK/FAIL | Gate G4 |
| An acceptance checkbox is a fact: ticked only after all runs and review approval; unverifiable items stay unticked with a note | Gate G6 |
| Auto-QA: a scenario must assert (`check()`, exit code, console/pageerror); isolated stand; database reset before each scenario; one full run at release, recorded | QA suite generation |
| Browser QA runner: isolated Compose stand, headless Chrome, scenario modules, console/pageerror capture | QA stage in Docker; non-zero exit on any failure |
| External change reconciliation: diff, record, update spec, continue | `forgel sync`; never reset or overwrite |
| A repeated full run is refused by the runner, not by prose | D-023 |
| Release plan: `[ ] [~] [x] [-]` statuses, links added as they appear, a verdict for every open item, no silent carry-over | Release train |
| Preflight audit: parallel agents over areas, diff against the tag, regressions/security/migrations/N+1, external APIs checked against source, critical/major fixed or accepted by the owner | Gate G7 |
| Deploy record: a database row exposed by API and read by triage; "fixed" means absent after deploy | `record_deploy` in the provider plugin |
| Error registry is cross-version, one row per cause, hashes in an appendix; triage → record → delete | Program telemetry |
| The queue is closed, the instruments are read; every complaint and every conversation gets a verdict | Improvement loop |
| The acceptance criterion is "did the product do its job for the user", not only "does it match the spec" | Gate G6 |
| Incident runbook: honest state, no versions/hosts/stack traces/PII/ETAs; review afterwards | Generated runbook |
| "AI writes the spec, not the code": declarative spec + deterministic engine | D-021 |
| Context: source read once → derivative; retrieval instead of dumping; conversation window; stable prefix; narrow typed tools | Agent runtime |
| No claim about state without in-session evidence; a document is evidence as of its revision date | Evidence discipline |
| Global settings only via env, not chat commands | Chat changes one project only |

### 7.2 What Changes at the Meta Level

In single-repo practice, "we only write what we do here" and "never wait for the frontend" are correct: a repository does not control someone else's scope. Forgel owns the whole graph, so the rules invert.

| Repo-level rule | Why it does not transfer literally | Forgel rule |
|---|---|---|
| The plan covers only this repo | A feature crosses 2+ repos | The unit of planning is a **change set** with a repo list |
| "Waiting for the frontend" is forbidden | At the meta level the dependency is real | A dependency is an explicit edge in `program.yaml`; a blocked status names the edge and the unblock path; there is no silent waiting |
| A release is one repo's version | The product ships as a set of versions | **Release train**: repo versions + integration stand + one plan/QA/audit |
| The repo owner fixes the error | The cause may be in a contract or another repo | The fix is owned by a repo; triage and correlation happen at the program level |
| A tracker task is for a UX change | One change set produces tasks in several repos | Program acceptance task + repo implementation tasks |
| Documents live in the repo | Some decisions are above the repo | Program docs are the source of truth; repo docs are derived |
| The model is inherited | Routing by role and cost is required | Core policy; the agent does not choose its model (D-022) |
| The owner starts local services | A sandbox exists | The sandbox starts and stops everything itself |

### 7.4 Program-Level Telemetry Loop

At the start of every program cycle, and continuously after production:

1. **Instruments:** product metrics, technical metrics, cost, deploy records, the error registry.
2. **Queue:** failures, complaints, conversations. Read everything; every complaint and every conversation gets a verdict.
3. **Correlation:** errors are matched against deploy records across all repos; "fixed" means absent after deploy.
4. **Record before closing:** the registry and journal are updated before the queue is cleaned.
5. **Findings → plan:** each becomes a change-set item, not a "someday".
6. **Criterion:** did the product do its job for the user, not only match the spec.
7. **Production changes** only after human approval.

### 7.6 Coexistence and External Changes

Forgel is a tool, not a religion. A user may generate a prototype, edit it by hand, or continue in another harness. This is a supported workflow, not a violation.

- Git is the source of truth. Forgel never requires a clean tree or its own commit history.
- Never `git reset --hard`. Never overwrite a file without a conflict check.
- Before each cycle, reconcile: detect changes since the last checkpoint, record them in `docs/program/external-changes.md`, classify them, and ask the user for a decision in `docs/program/reconciliation.md`. The command is `forgel sync <project-id> [--from <stage>] [--force]`.
- `forgel reconcile <project-id> --decision accept|fix|rollback|ignore [--notes "..."]` records the decision. `accept` documents the change in the feature spec; `fix` blocks at review until fixed; `rollback` restores the baseline; `ignore` records and continues.
- `forgel run` refuses a pending reconciliation. Only a recorded decision starts a new ledger generation; affected gates (spec review, QA, acceptance, audit) run again while the old history is preserved.
- Forgel commits its own generation snapshots and moves the `forgel-baseline` git tag. Edits after that tag are the external changes `sync` reports.
- Gates run against the current code, not the generated baseline.
- Generated code contains no proprietary hooks or hidden state. All state lives in standard files.
- Leaving is always possible: export the repositories, keep the Dockerfiles, and drop Forgel.

### 7.7 Long-Running Orchestrator and Iterations

Forgel runs as a daemon: it picks projects with pending work, runs one iteration, and then waits. It never loops on a completed project, and it never polishes endlessly.

**Iteration.** An iteration has:

- a goal (for example, "ship the MVP"),
- a definition of done (acceptance criteria + audit),
- a scope (change sets),
- a budget (per feature and per project).

It starts on a trigger: a user request, a release milestone, a telemetry threshold, or a scheduled review. It closes with a recorded verdict: goal met, budget exhausted, blocked, or cancelled.

**Daemon loop:**

- `forgel daemon` polls the ledger;
- runs projects that are not done and have no blocking reconciliation;
- logs and skips a project waiting for a user decision;
- idles when there is nothing to do.

**Stop conditions:** all acceptance criteria pass and the audit is clean; or the budget is exhausted; or a blocking reconciliation/decision is pending; or no progress is possible.

**Post-release triage:**

| Class | Examples | Action |
|---|---|---|
| Auto-fix | money-path double charge, security defect, deterministic regression | Fix, test, canary, rollback plan; production still needs human approval |
| Ask user | ambiguous product behavior, scope change, risky migration, legal question | Present the evidence and options; wait for a decision |
| Record / defer | one-off complaint, low-signal anomaly, potential performance issue | Record in the telemetry registry; revisit when the threshold is crossed |

Never: an unbounded improvement loop, a change without a change set and acceptance criteria, or an automatic production deploy.

### Release Policy After the Goal

SemVer governs the proposal class:

| Class | Examples | Default | Config |
|---|---|---|---|
| PATCH | security, payments, broken user scenarios, regressions, data integrity | Forgel proposes a fix with evidence; it does not apply it without approval | `release.auto_patch = true` applies PATCH automatically (not recommended) |
| MINOR | new features, UX/scenario changes, metrics-driven improvements | Not proposed | `release.propose_minor = true` makes Forgel propose them |
| MAJOR | breaking changes, architecture, platform/store or legal changes | Human-initiated only | Never automatic |

Proposals are written to `docs/program/proposals/<id>.md` and delivered through the chat channel (Telegram in the MVP): what was found, the evidence, the proposed class and the risk. An approved proposal becomes a change set with its own acceptance criteria and budget.

### 7.8 Simplicity and Complexity Control

Coding models tend to accumulate requirements, branches, flags and backward-compatibility shims. Complexity compounds; a product that is "done" can become unmaintainable. Forgel treats simplicity as a gate, not a preference.

**Deterministic pre-filter.** Before review, count the patch since the generated baseline:

- added and removed lines;
- new files;
- new configuration keys in `forgel.toml`;
- compatibility markers (`deprecated`, `legacy`, `compat`, `backward`);
- added branches.

The budget lives in `[simplicity]` in `forgel.toml`. Exceeding it fails the review gate. The result is in `docs/program/complexity/report.md`; the metrics are in `metrics.json`. `forgel complexity <id>` recomputes the report.

**Simplicity Arbiter.** A clean-context role, independent of the developer. It reads the spec, the diff and the complexity report — never the developer's reasoning. It returns:

- **SIMPLIFY** with a concrete smaller alternative;
- **ACCEPT** with a rationale;
- **ESCALATE** to the user.

**Decision policy.** The arbiter has default authority for safe, internal, reversible simplifications:

- remove dead code, unused flags, duplicate abstractions and over-general configuration;
- remove a compatibility shim when no consumer is named (supported version, telemetry, or contract);
- replace a one-off flag or branch with a spec/recipe change when the behavior is unchanged.

It asks the user only when the change is user-visible, changes a public contract or data model, touches money, legal or compliance, is irreversible, or the requirements genuinely conflict. Otherwise it decides and records the decision in an ADR; the user receives one digest per iteration, not a question per change.

**Rules:**

- No speculative generality: a new flag, abstraction or branch needs a second consumer or an explicit requirement ID.
- No backward-compatibility shim without a named consumer and a removal date.
- Prefer changing the task framing over adding a branch.
- Reserve part of each iteration for deletion and simplification; track the net complexity delta.
- A budget exception is a recorded decision, never a silent override.

### 7.9 Refactoring Policy

Agents often append branches to existing code where a small targeted rewrite would be clearer. Refactoring is not the default, and refactoring for every requirement is a failure mode of its own.

**Default: NO_REFACTOR.** Extend the existing structure with the smallest change that satisfies the requirement.

**A refactor is justified only when:**

- the new requirement cannot be implemented cleanly without changing the structure — not merely because a rewrite is aesthetically nicer;
- the cost of extending and maintaining the current code over the planning horizon exceeds the cost of the refactor;
- the refactor is bounded, behavior-preserving, covered by tests, and reduces net complexity;
- it prevents a known class of defects or removes an unclaimed compatibility shim.

**Decision classes:**

| Class | Scope | Authority |
|---|---|---|
| NO_REFACTOR | default; extend in place | Developer |
| TARGETED_REFACTOR | one module or function; behavior-preserving; bounded files and lines | The Simplicity/Refactoring Arbiter may auto-apply internal, net-complexity-reducing changes |
| STRUCTURAL_REFACTOR | cross-module, public contract, data model | Proposal + human approval |
| DEFER | record as technical debt with a trigger | `docs/program/technical-debt/<id>.md` |

A refactoring proposal (`docs/program/refactoring/<id>.md`) records the current design, the new requirement, the cost of extension, the cost of the refactor, the maintenance cost, the risks and the alternatives.

**Signals, not verdicts.** Append-only files (many added lines, almost none removed), files above a size threshold, high branch density and repeated edits to the same area are surfaced in the complexity report. Extending code is the default; the arbiter decides whether the signal justifies a refactor.

**Config:** `[refactoring] enabled`, `budget_percent` (maximum share of an iteration), `allow_auto_targeted`.

### 7.10 Budget Control

Forgel must never let an agent consume an unbounded budget. This is a rare but catastrophic failure mode: an agent hits a misconfigured environment, starts working around it, retries without progress, and keeps calling the model until the provider balance — or the card behind an auto top-up — is exhausted. DeepSeek and similar providers do not enforce a budget on an API key; the harness must.

**Layers:** per call, per feature, per iteration, per day (UTC reset), per project, per provider key.

**Caps and thresholds:**
- **Warn** at `warn_percent` (default 80%): notify the user, reduce model quality for non-critical work, pause low-priority proposals.
- **Hard stop** at 100%: stop before the next call, record the checkpoint and ask the user. No silent overrun.
- **Spend-rate cap** (`max_spend_per_hour_usd`): anomaly circuit breaker.
- **No-progress cap** (`max_retries_without_progress`): repeated identical errors, retries without new evidence, or environment workaround loops stop the iteration.

**Budget Arbiter.** A clean-context role watches the budget ledger, spend rate and progress. It can pause or stop; it can never increase a budget. Only the user can raise it. Every stop records the reason and the checkpoint.

**Provider-key isolation:**
- a separate, scoped API key per project/environment, never the user's main key;
- prepaid balance, auto top-up disabled;
- balance monitoring where the provider exposes it, otherwise a mandatory egress proxy enforces the cap;
- the proxy is the only path to the model endpoint; agents and plugins cannot bypass it.

**Enforcement points:** the agent runtime before every model call; the plugin host before tool calls; the daemon before starting an iteration; a global `forgel pause` / `forgel stop` switch and Telegram commands.

**Artifacts:** `docs/program/budget/report.md`; ledger `cost` per event; stop records.

**Resume:** a stopped iteration keeps its checkpoint. After the user raises the budget or fixes the environment, `forgel run` continues from the checkpoint; no work is lost.

**Config:**

```toml
[budget]
per_feature_usd = 10
per_iteration_usd = 100
per_day_usd = 20
per_project_usd = 300
warn_percent = 80
max_spend_per_hour_usd = 10
max_retries_without_progress = 3
```

**Metrics:** daily spend; cost per accepted feature; budget stops per iteration; overspend incidents (must be 0); no-progress stops; cost-estimate error.

**Risks:** provider-key exhaustion or auto top-up; key leakage; a subagent bypassing the ledger; estimate drift; false stops; ignored warnings.

### 7.11 Git and GitHub Integration

Forgel currently uses local git per project: `git init`, a baseline commit, the `forgel-baseline` tag and generation commits. Remote integration is not implemented yet. The target flow for a daemon on a server:

1. **Auth:** a **GitHub App**, not a personal token. Installation tokens are short-lived (about one hour), scoped to selected repositories, with Contents read/write, Pull requests read/write, Checks read and Metadata read. The private key lives in a secret manager; a token is minted per job and never written to disk or logs. A single-user self-host may use a fine-grained PAT or a deploy key, but the App is the default.
2. **Clone and fetch:** `git fetch origin` before every iteration. Clone into a workspace, never into the running daemon's own code directory.
3. **Branch:** never commit to `main`. Create `forgel/<change-set>-<slug>` from the current `origin/main`. One branch per change set; the same name across repos in a multi-repo change set.
4. **Commit:** one logical change per commit; English messages; bot identity (`Forgel <bot@forgel.io>`), not the user; no harness attribution. Add sign-off only when the target repo requires DCO.
5. **Push and PR:** push the branch and open or update a draft PR with the spec, acceptance evidence, complexity report, jurisdiction disclaimer and rollback note. The PR is the review unit; never force-push a protected branch.
6. **CI and checks:** require the repository's checks and wait for them through the Checks API or a webhook. On failure, fetch the logs, triage and fix on the same branch. Forgel's own QA passes before the PR is marked ready.
7. **Merge:** **auto-merge by default** after every gate and required check passes; `merge = "human"` leaves the PR for a final human review. Protected `main`, linear history, no direct pushes, no force pushes.
8. **Upstream sync:** fetch before an iteration. If `main` moved, rebase the branch; if it conflicts, stop and ask the user. Never `reset --hard` or force-push.
9. **Multi-repo change sets:** one PR per repo, linked by a change-set ID; merge order follows the contracts; the integration environment is built from the pinned SHAs. Cross-repo merge is not atomic; the change set is accepted after all PRs merge and integration passes.
10. **Repo onboarding:** `forgel adopt <repo-url>` clones the repo, detects the stack, writes `program.yaml`, `forgel.toml`, `FORGEL.md` and `AGENTS.md`, creates the baseline tag and opens an onboarding PR. Generated projects require the user (or an App with template permission) to create the repo; Forgel never pushes directly to `main`.
11. **Events:** GitHub App webhooks for push, pull request, check run and issue events; polling is the fallback for a minimal self-host.
12. **Self-update:** the daemon runs from a released image, not from the working copy it modifies. Merging Forgel changes triggers CI to build a new image and the deploy updates it.

**Merge modes:**

- **`auto` (default):** Forgel merges its own PR after review, QA, acceptance, audit, complexity/simplicity gates, green CI, no blocking reconciliation, budget within cap, branch up to date and no conflict. A merge queue serializes merges. Post-merge smoke runs on `main`; a failure triggers an automatic revert and a stop.
- **`human`:** the PR is left for a human decision after the same gates. Use it for teams or repositories whose policy requires human review.
- **MAJOR changes are not auto-merged:** they remain human-initiated and reviewed.
- If branch protection requires a human review that Forgel cannot satisfy, it falls back to `human`; it never tries to bypass protection.

**Config:**

```toml
[git]
provider = "github"
auth = "auto"                # auto | github_app | pat | deploy_key
base_branch = "main"
branch_prefix = "forgel/"
draft_pr = true
require_ci = true
merge = "auto"               # auto | human; auto is the default
auto_revert_on_failure = true
```

**Artifacts:** PR URL, commit SHA and merge SHA in the ledger; `docs/program/git/report.md`.

**Metrics:** direct pushes to `main` = 0; force pushes = 0; PRs with acceptance evidence = 100%; PR cycle time; conflict rate; CI pass rate; merge rate.

**Risks:** token leakage; branch-protection bypass; force-push; upstream conflicts; large PRs; rate limits; webhook spoofing.

### 7.12 Deployment Modes

Production deploy has three modes, configured in `[deploy]`:

| Mode | Behavior | Default |
|---|---|---|
| `auto` | Forgel deploys without confirmation | Disabled; explicit opt-in; not recommended |
| `confirm` | Forgel prepares the release, asks the user in Telegram (Deploy / Cancel), then deploys | Default when a deploy provider is configured |
| `manual` | No deploy pipeline is configured; Forgel produces the release bundle, runbook and instructions, then stops | Automatic fallback when no provider is configured |

- **`confirm`** is the default when a deploy plugin exists. Approval is recorded in the ledger with the user, time, release SHA and the compliance acknowledgement.
- **`auto`** requires explicit configuration and a one-time compliance acknowledgement. It still records the deploy and runs post-deploy verification; failure triggers a rollback where supported and a PATCH proposal.
- **`manual`** is not a failure: the iteration closes with a release artifact and instructions for the human.
- Every deploy writes `docs/program/deploy/report.md` and a deploy record: mode, release SHA, tag, time, approver (if any), health-check result.
- Legal gates — legal entity, payments, app stores, jurisdiction acknowledgement — are separate and always human.

**Config:**

```toml
[deploy]
mode = "confirm"        # auto | confirm | manual
health_check_url = ""
rollback = true
```

**Delivery:** `forgel deploy up` (D-069) is the installation path: a local
`.env.deploy` holds the target, image strategy and runtime configuration; the
utility writes the production Compose file and a `0600` env to the server over
SSH. Publishing the image to GHCR is recommended for versioned releases;
remote build keeps the first self-host registry-free.

### 7.13 Project Environments

A project environment is a declarative container artifact, not a core adapter:
an OCI image (or Dockerfile/Compose/Dev Container) plus a small contract for
the commands Forgel needs.

```yaml
# environment.yaml — a project artifact
image: python:3.12-slim        # or: build: environment
repo: api                      # commands run here; default: the sole repository
mounts: [web]                  # sibling repositories, mounted read-only
services: [compose.yaml]       # optional
setup: ["pip install -r requirements.txt"]
test: ["python -m unittest discover -s tests"]
e2e: ["python e2e/check.py"]
env:                           # optional, added to every command
  PYTHONPATH: src
ports: [8000]
health: "/health"
```

The contract lives in the control repository, or in the sole repository of a
brownfield project next to the code; the control copy wins when both exist.
`build` and `services` paths are relative to the file's own directory, so a
repo-committed contract stays portable. `mounts` lists sibling repositories by
id; the sandbox mounts them read-only at `/<id>`, so an e2e can inspect the
product without exposing the rest of the project. The file is a strict YAML
subset: top-level keys, scalar values, flow lists, block lists and one level of
nested mapping (`env`). A
malformed contract fails QA loudly; a project without one keeps the legacy
fallback (the template e2e script), so existing projects are not broken. The
local single-tenant fallback runs `test` and then `e2e` on the host and the
interpreter that runs Forgel; `setup` belongs to the environment image and is
executed by the sandbox runtime. The docker QA stand still starts its compose
file; routing it through the contract is part of the sandbox work.

The core reads this contract and runs it inside the per-project sandbox. It
does not know language-specific commands. Official recipes provide starting
images and compositions for common stacks; the agent may create or extend an
environment definition for a missing stack, but only as a standard, committed,
reviewable artifact — never as a bespoke adapter inside the core.

Sandbox boundary: repo-only mount, no `/data` secrets, no host Docker socket,
resource and network limits, configurable registry policy (allowlist and
pinned digests for multi-tenant; arbitrary images allowed for a trusted
single-user host). The daemon never mounts `/var/run/docker.sock`; it reaches
a dedicated Docker engine over `DOCKER_HOST`. `FORGEL_SANDBOX=docker` starts one
labelled container per session: the selected repository at `/workspace`, the
daemon UID/GID, all capabilities dropped, `no-new-privileges`, a read-only root
with a writable `/tmp`, CPU/memory/pid limits, `network=none` by default, and
the image policy from `FORGEL_SANDBOX_IMAGES`/`FORGEL_SANDBOX_REQUIRE_DIGEST`.
Coding-agent `run` actions and the contract's `setup`/`test`/`e2e` commands run
inside it; file actions stay on the mounted repository.

This choice is (c) at the execution layer, (b) at the artifact layer and (a)
for convenience: arbitrary environments are allowed, but only behind a
sandbox; missing environments are authored as standard container definitions
rather than adapters; official recipes cover the common cases.

### 7.14 Autonomy Policy

The product removes the human from the critical path. Human involvement is an
exception, not a step (D-075).

**Rule.** Work autonomously. The task is the source of truth. Do not ask for
permission to start, continue or finish. When a detail is unspecified but the
action is reversible, choose the simplest option consistent with the
requirements, record it as an assumption and continue. Review is result-first:
finish the whole requested result, present it with evidence, and rework on
feedback.

**Stop conditions — the only reasons to involve a human:**
1. a material fork: two interpretations produce materially different products
   and the wrong one wastes a full cycle;
2. an irreversible or destructive action: deleting data, rewriting history,
   force-push, production deploy, payments, secrets, legal decisions;
3. missing access or credentials.

Ask one consolidated question, never a dialogue. In the coding protocol, where
the agent cannot ask, the same cases are a `fail` with the exact decision
needed.

**Pre-release vs production.** Before a release, err on the side of doing:
staging is reversible, and showing a finished result is cheaper than an
interrogation. In production, be conservative with product data, customer
credentials, money and legal exposure; those actions are human-gated by
default.

**Evidence.** Every assumption is recorded in the task record and in the agent
report. The human reviews assumptions and the result, not a stream of
questions. A wrong assumption is a normal input to the next change, not a
process failure.

**Gates are not questions.** The staging and production approvals are
checkpoints on a finished result, not a confirmation during work. Keeping the
two apart is what makes the loop fast: the work runs to completion, then a
human decides once.

| Auto-deploy regression | High | Opt-in only, health checks, rollback, canary; `confirm` is the default |

| Confirmation fatigue | Medium | Confirm only for production; batch releases |

## 13. Definition of Success

By the end of M1:

- The same brief from 3–5 different teams produces a working staging environment in comparable time.
- Acceptance rate ≥ 60%.
- No project requires manual code intervention.
- 100+ OSS installs, 10+ external issues/PRs.
- Every accepted change set has acceptance evidence: criteria, runs, review.
- Every production deploy records the jurisdiction pack, its review status and the user's compliance acknowledgement.
- `docker compose run --rm forgel demo` works on a clean machine.
- The generated product's E2E runs in Compose with a headless browser.
- A project modified by hand or another harness can be resumed without resetting the process.
- Every iteration ends with a recorded verdict: goal met, budget exhausted, blocked, or cancelled.
- Every post-release proposal carries its SemVer class, evidence, risk and approval state.
- Every complexity-budget violation has a recorded decision: simplify, accept with a rationale, or change the spec.
- Every structural refactor has a recorded cost/benefit decision; deferred debt has a trigger.
- A real Forgel change is delivered through Forgel itself in the self-hosting milestone.
- No overspend incidents: every agent run stops at its budget or on no progress, with a recorded checkpoint.
- No direct pushes to `main` and no force pushes; every change lands as a reviewed PR with evidence.
- A change can land on `main` without a human merge when all gates pass; human merge is opt-in.
- Every deploy records its mode, release SHA, health result and approver (or a manual release bundle).

By the end of M2:

- 10+ third-party plugins, 500+ installs, 20+ external contributors.
- An international cloud is added by a plugin without core changes.
- A second jurisdiction pack is added without core changes.
- No "fixed" status without the error being absent after deploy.

By the end of M3:

- The hosted version is available; OSS remains free.
- 1000+ OSS installs.
